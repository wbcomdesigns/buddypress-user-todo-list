# Audit Verdict: buddypress-user-todo-list (branch 3.6.0)

Static-only self-audit. No browser tools used (another agent owns the browser). No code was modified or committed.

## Shippable? WITH FIXES
Core member/AJAX flows are wired correctly and the recent QA-card fixes (native `alert()`/`confirm()` removal, dark-mode tokens, modal button styling) are confirmed landed on this branch. The blocking issues are two unbounded/N+1 queries in the group Overview and group List views and a silent 500-task cap with no true pagination on the member list — all big-site-readiness violations per the mandatory checklist, not "is it broken today" bugs. Small/medium communities will not notice; a busy group (1000+ tasks) will see slow/timeout page loads and, past 500 tasks, invisible/unmanageable member tasks.

## Sellable? WITH POLISH
Solid architecture (CPT + postmeta, no custom tables, proper nonce/capability checks on every inspected AJAX handler, no raw SQL, correct single text domain). Held back from "yes" by: 16 unlabeled form inputs + 10 `outline:none` rules with no `:focus-visible` replacement (real a11y regression for keyboard users across admin and frontend), and heavy raw-hex/px drift in the consumer-facing `bptodo-front.css` that won't track the design-system tokens.

### Verified NOT bugs (false positives from the automated scanner, confirmed by manual read)
- **"9 broken-ajax" findings from `wppqa_scan_plugin`** — the scanner's regex only matches `add_action('wp_ajax_...', 'callback')` and missed this plugin's custom `$this->loader->add_action(...)` wiring pattern (`includes/class-bptodo.php:241-281`). Manually verified: `bptodo_complete_todo`, `bptodo_undo_complete_todo`, `bptodo_remove_todo`, `bptodo_add_todo_category_front`, `bptodo_export_my_tasks`, `bptodo_edit_form_popup`, `bptodo_update_form_popup`, `bptodo_get_todo_card_html`, `bptodo_display_group_todo_report` all have real handlers in `public/class-bptodo-public.php`, each with `check_ajax_referer()` + an ownership/capability gate (post author OR `edit_others_posts` OR group admin/mod).
- **`admin_email` / `date_format` / `time_format` "stale-read"** — these are WordPress core options read with safe fallbacks, not options this plugin is expected to write. Not a bug.
- **`data-retention-settings` / `group-todo-list-settings` / `user-todo-list-shortcodes` "written-never-found"** — these are persisted via `register_setting()` + WP core's `options.php` Settings API handler (`admin/class-bptodo-admin.php:185-186, 240`), which the static writer-detector doesn't recognize as a write site. Verified real via the form markup + `register_setting` call. Not a bug.
- **Native `alert()`/`confirm()` (flagged in this plugin's own `CLAUDE.md` onboarding notes)** — confirmed fixed on this branch; `assets/js/bptodo-front.js:452-460`, `admin/assets/js/bp-todo-list-admin.js:66`, and `assets/js/admin.js` now route through `BPTodo.modal.confirm()`.
- **SQL injection** — the only 3 raw `$wpdb->` usages (`inc/class-bptodo-globals.php:102-114`, `public/todo/group/list.php:28-34`) are all wrapped in `$wpdb->prepare()` with `%d`/`%s` placeholders. Clean.
- **i18n** — all 267 translation calls in scope use the single correct text domain `wb-todo` matching the plugin header; no mismatched-domain strings found. Not audited: full translator-comment coverage on every placeholder (spot-checked, looked correct).
- **Three-entry-points** — this plugin has 0 REST endpoints by design (frontend AJAX + admin Settings API only, matches `audit/manifest.json`); not a Free/Pro data-store split like the SaaS-style plugins the "three entry points" rule targets, so not flagged as a gap.
